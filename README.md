# LogSentinel 🛡️

**A lightweight, rule-based threat detection engine for Linux, Windows and web server logs, with every rule mapped to MITRE ATT&CK.**

LogSentinel does one slice of a SOC analyst's day: it takes raw logs from several sources, puts them into one common event format, runs detection rules over them (single-event, threshold and sequence rules), and produces triage-ready alerts in the terminal, as JSON (for a SIEM/SOAR) or as an HTML report.

It runs on the Python standard library alone, so there's nothing to install.

## Why I built this

SIEMs like Splunk, Elastic and Sentinel run on correlation rules. I wanted to understand how they work underneath, so I built a small engine myself. I worked out how to normalise different log formats, how to write sliding-window threshold logic without flooding the analyst with duplicate alerts, and how to chain events into a sequence detection (e.g. *brute force → successful login → privilege escalation*). The bundled sample logs are synthetic but modelled on the attack chain I run in my home lab (Kali → Ubuntu web server + Windows 10 VM), so you can reproduce every detection without a lab.

## Features

| | |
|---|---|
| **Log sources** | Linux `auth.log`/`secure` (sshd, sudo, su, useradd, usermod), Windows Security/System/PowerShell events (JSON export), Apache/Nginx combined access logs |
| **Rule types** | `match` (single event), `threshold` (N events or N *distinct* values per group in a sliding window), `sequence` (A × N followed by B) |
| **Detections** | 20 bundled rules: brute force, password spraying, login after brute force, root shells via sudo, backdoor accounts, privileged group changes, log clearing, encoded PowerShell, malicious services, SQLi, path traversal, XSS, scanner user agents, directory brute force |
| **Threat mapping** | Every rule tagged with MITRE ATT&CK technique IDs, linked in the HTML report |
| **Alert quality** | Ongoing activity extends one alert instead of creating duplicates; evidence lines attached to each alert |
| **Output** | Coloured console summary, JSON, self-contained HTML report |
| **Automation** | `--fail-on critical` returns exit code 2 so it can gate scripts or CI jobs |

### Command line options

```
python -m logsentinel PATH [PATH ...] [options]

  -r, --rules FILE|DIR     custom rule file/dir (repeatable; default: bundled rules)
  -f, --format FORMAT      auto | linux_auth | windows | web
  --year YEAR              year for syslog lines that have none
  --min-severity LEVEL     hide alerts below this level
  --json FILE              write alerts as JSON
  --html FILE              write HTML report
  --fail-on LEVEL          exit code 2 if any alert >= LEVEL
  --list-rules             show loaded rules
```

## The sample scenario (incident walkthrough)

`samples/` holds an attack chain generated by `scripts/generate_samples.py`, with normal user activity mixed in. Here's what LogSentinel reconstructs:

|---|---|---|---|---|
| 03:03 | Recon | 24 requests from `gobuster/3.6`, 21 × 404 | LS-019, LS-020 | T1595 |
| 03:07 | Initial access attempt | `sqlmap` UNION/SLEEP payloads, `../../etc/passwd`, `<script>` | LS-016/017/018 | T1190 |
| 03:15 | Credential access | 14 failed SSH logins for `root`, then 7 different usernames | LS-001, LS-002 | T1110.001/.003 |
| 03:18 | **Compromise** | `Accepted password for deploy from 192.168.56.101` | **LS-003** | T1078 |
| 03:19 | Priv-esc + persistence | `sudo /bin/bash`, `useradd sysupdate`, added to `sudo` | LS-004/005/006 | T1548.003, T1136, T1098 |
| 03:30 | Lateral movement | 13 × 4625 over RDP, lockout, 4624 type 10 as `jsmith` | LS-007/008/009/015 | T1110, T1078 |
| 03:32 | Execution | `powershell -nop -w hidden -enc ...` download cradle | LS-013 | T1059.001, T1027 |
| 03:33 | Persistence | `svc_backup` created and added to Administrators; service `C:\Users\Public\winupd.exe` | LS-010/011/014 | T1136, T1098, T1543.003 |

The benign activity (a user mistyping a password once, `sudo apt update`, normal browsing) does **not** raise alerts, and the tests check that.

## Writing rules

Rules are plain JSON (`logsentinel/ruleset/default_rules.json`). Drop your own files in a folder and pass `-r myrules/`.

```json
{
  "id": "LS-003",
  "title": "Successful SSH login after brute force",
  "severity": "critical",
  "mitre": ["T1110", "T1078"],
  "source": "linux_auth",
  "type": "sequence",
  "sequence": {
    "first": {"match": {"event_type": "ssh_failed_login"}, "count": 5},
    "then":  {"match": {"event_type": "ssh_successful_login"}},
    "window_seconds": 900,
    "group_by": ["src_ip"]
  }
}
```

Supported conditions: exact value (case-insensitive), list (`in`), `regex`, `contains`, `startswith`/`endswith`, `gt`/`gte`/`lt`/`lte`, `exists`, `not`, plus `any_of` for OR logic. Every event exposes `event_type, source, host, user, src_ip, message` plus source-specific fields (`command`, `group`, `target_user`, `logon_type`, `CommandLine`, `ScriptBlockText`, `ImagePath`, `status`, `path_decoded`, `user_agent` ...).

## Using it on real logs

**Linux:** `sudo python -m logsentinel /var/log/auth.log --html report.html`

**Windows:** run `docs/export-windows-events.ps1` as Administrator, then analyse the JSON it writes:

```powershell
.\docs\export-windows-events.ps1 -Hours 24 -OutFile C:\Temp\win.json
python -m logsentinel C:\Temp\win.json --html report.html
```

**Web server:** `python -m logsentinel /var/log/apache2/access.log`

## Architecture

```
 raw logs ──► parsers.py ──► Event (normalised schema) ──► engine.py ──► Alert ──► report.py
             auth / win / web                               match            console / JSON / HTML
                                    rules.py (JSON rules) ──► threshold
                                                              sequence
```

## Tests

```bash
python -m unittest discover -s tests -v
```

There are 21 tests covering the parsers (including the PowerShell 5.1 `/Date()/` format and .NET 7-digit timestamps), every rule operator, window and grouping logic, false-positive checks, CLI exit codes and HTML escaping of untrusted log content (so a payload in a log can't inject script into the report). They run on GitHub Actions on every push.
